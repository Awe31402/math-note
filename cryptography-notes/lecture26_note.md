## 1. 金鑰建立的分類

`[00:04]` **金鑰建立（key establishment）** 粗分兩種：

```
              金鑰建立
             /        \
     金鑰傳送          金鑰協議
  (key transport)   (key agreement)
```

【課堂討論】`[00:05]` 金鑰傳送裡，誰選金鑰？
→ **一方選金鑰，再傳給別人**。可能是 Alice 選、Bob 選，或第三方選再傳給兩人。

**金鑰協議**：**雙方都參與**產生金鑰。

【課堂討論】`[00:06]` 哪一種比較安全？
- 學生答：雙方都參與的話，第三方比較難操縱。
- 教授：「好點子。但我們的假設是**兩種都要能抵擋 Oscar**，所以這只算一點點理由。」

【口頭】`[00:07]` 教授給的另一個理由：**弱金鑰（weak key）**
- 有些區塊密碼（不是 AES，但例如 **DES**，或 **IDEA**）有所謂**弱金鑰**：例如有 $2^{128}$ 把金鑰，其中某些是弱的。
- 假如 Alice 的電腦有**病毒**，病毒操縱她挑一把弱金鑰。
- 如果**雙方都參與**產生金鑰，就**很難主動造出一把弱金鑰**。

【課堂討論】`[00:08]` 我們學過哪個金鑰協議？→ **Diffie-Hellman**
$$k_{AB} = \alpha^{ab}$$
$a$ 是 Alice 的秘密、$b$ 是 Bob 的秘密 → **雙方都貢獻**，所以是金鑰協議。

| | 金鑰傳送 | 金鑰協議 |
|---|---|---|
| 誰決定金鑰 | 一方（或第三方） | 雙方都貢獻 |
| 例子 | **KDC 協定**（今天） | **Diffie-Hellman** |

【課本補充】
- 理想上，金鑰協議中**沒有任何一方能控制**最後的值。
- 金鑰建立跟**身分識別**密切相關：要防止有人冒充 Alice 或 Bob 混進協定，每一方都必須確定對方的身分。

## 2. 【課本補充】金鑰新鮮度與金鑰衍生

課堂沒講，依課本 §13.1.2 整理（第 5.2 節「金鑰新鮮度」有用到這個概念）。

**會期金鑰（session key / ephemeral key）**：只在有限時間有效的金鑰，例如一次網路連線。

限制金鑰使用時間的好處：
1. 金鑰外洩時**損失比較小**
2. 攻擊者手上用同一把金鑰加密的密文**比較少**，比較難攻擊
3. 攻擊者想解更多明文，**得破好幾把金鑰**

實例：**GSM 手機**語音加密、**付費電視衛星**影像加密 —— 幾分鐘甚至幾秒就換新金鑰。

**怎麼更新金鑰？**
- 方法一：把金鑰建立協定**再跑一次**（有通訊和計算成本，公鑰尤其貴）。
- 方法二：用已經共享的秘密 $k_{AB}$ **衍生**新的會期金鑰 → **金鑰衍生函數（KDF, Key Derivation Function）**。

```
   k_AB ──┐
          ├──→ [ KDF ] ──→ k_ses
   r ─────┘   （r 不是秘密）
```

**KDF 必須是單向函數**：就算某把會期金鑰外洩，攻擊者也**推不回 $k_{AB}$**（否則就能算出所有其他會期金鑰）。

**用 nonce 衍生**（nonce = 只用一次的數字）：

```
   Alice                          Bob
                                  產生 nonce r
            ←────── r ──────
   k_ses = e_{k_AB}(r)            k_ses = e_{k_AB}(r)
```

其他做法：

| 做法 | 公式 | 說明 |
|---|---|---|
| nonce + 加密 | $k_{ses} = e_{k_{AB}}(r)$ | 要送一次 $r$ |
| nonce + HMAC | $k_{ses} = \text{HMAC}_{k_{AB}}(r)$ | 第 25 講 |
| 計數器 + 加密 | $k_{ses} = e_{k_{AB}}(\text{cnt})$ | **不用傳任何東西**，但雙方要知道何時該換 |
| 計數器 + HMAC | $k_{ses} = \text{HMAC}_{k_{AB}}(\text{cnt})$ | 同上；不同步時可能要送同步訊息 |

## 3. n² 金鑰分配問題

`[00:09]` 最基本的做法，叫 **n² 金鑰分配**。
【口頭】「我叫它**問題**，不確定別人是不是也這樣叫。」

### 設定

`[00:10]` 小網路，$n = 4$ 個使用者：**Alice、Bob、Chris、Dorothy**（簡稱 **Dor**）。
- 每個人都要能跟其他每個人私下通訊：Alice 跟 Chris 講話時，Bob 和 Dor 不能偷聽。
- 【口頭】「像 email 和網際網路，只是不是 4 個人，而是十億個人。」

**每一對使用者共享一把金鑰**：

| 使用者 | 持有的金鑰 |
|---|---|
| Alice | $k_{AB}, k_{AC}, k_{AD}$ |
| Bob | $k_{AB}, k_{BC}, k_{BD}$ |
| Chris | $k_{AC}, k_{BC}, k_{DC}$ |
| Dor | $k_{AD}, k_{BD}, k_{DC}$ |

### 要有安全通道

`[00:13]`【口頭】這裡**默默假設**了一件事：要建立這些金鑰，需要**安全通道（secure channel）**。
- 例如**系統管理員**親自跑到 Alice 那裡上傳三把金鑰，再去 Bob 那裡上傳三把……
- 「**只要是對稱密碼，某個時間點總需要一個安全通道。**」

### 數金鑰

`[00:14]` $n$ 個使用者：

| 項目 | 數量 |
|---|---|
| 每人存幾把 | $n - 1$ |
| 系統裡總共幾把金鑰 | $n(n-1) \approx n^2$（所以叫 **n² 問題**） |
| 金鑰**對**有幾對 | $\dfrac{n(n-1)}{2} = \dbinom{n}{2}$ |

【課堂討論】金鑰是成對的（每把金鑰都有一個對應），所以除以 2 → 學生答對。
【口頭】「這數學上不太好看。」

### 缺點一：數量是平方成長

`[00:15]`【口頭】「$n^2$ 聽起來不壞，**代入數字就開始可怕了**。」

**例子**（`[00:16]`）：**750 名員工**的公司。
- 「這不是 IBM 或福特，這是**中型公司**。」
- 金鑰對數：$\dfrac{750 \times 749}{2} = 280{,}875$
- 「對一個小公司來說**大得驚人**。」

【口頭】`[00:17]` 但這數字本身是問題嗎？
- **對單一使用者**：只存 749 把，是**線性**的，還好。
- 但金鑰要**在某處產生**：需要一個 **TA（Trusted Authority，可信任機構）**，例如系統管理員，產生並推送出去。**成本很高**。

【課本補充】例 13.1：總共要產生 280,875 個金鑰對，要經由安全通道分配 $750 \times 749 = 561{,}750$ 把金鑰。

### 缺點二（最嚴重）：加入新使用者很麻煩

`[00:18]`【口頭】「**加入新使用者很複雜** —— 這是很有禮貌的說法，其實就是**很痛苦**。」

新使用者 **Noah**（第 5 人）：
1. Noah 需要一整組金鑰 $k_{AN}, \ldots, k_{DN}$ → 管理員到 Noah 的電腦**手動安裝**。
   - 【口頭】「你可能說沒什麼。我們研究室來了新博士生，系統管理員本來就要去設定電腦。」
2. 【課堂討論】`[00:19]` 但 Noah 現在能跟 Alice 通訊嗎？→ **不行**，Alice 需要更新。Bob、Chris、Dor 也都要更新。

`[00:20]` 750 人的公司請了新秘書（第 751 人）：
- 新秘書的電腦要裝所有金鑰 —— **也許還行**。
- **完全無法接受的是**：要跟**所有現有使用者**都建立**安全通道**。

【課本補充】要建立 **751 條安全通道**（750 個舊員工 + 新員工）。

### 什麼時候還是可以用

`[00:21]`【口頭】「我不是說這**完全愚蠢**。」
- 例：德國總部的中型公司，在法國、美國、中國各有一個業務據點 → 很適用。「**不會每天**都在捷克開新據點。」
- 條件：網路**小**，而且更重要的是**靜態**（沒什麼人來來去去）。
- 「我**本人知道**有些**銀行網路**用這種做法，在歐洲以外。」

## 4. KDC 協定

`[00:21]`【口頭】「可能有點出乎意料：我要給你們看一個**很實用的**金鑰分配方法，**不用 Diffie-Hellman**，而是**用 AES 或 3DES —— 對稱密碼**。」
- 「到目前為止，我們理解的是：要建 AES 金鑰，要嘛做**蠢事**（找個信差把金鑰帶過去），要嘛用 Diffie-Hellman。」
- 「接下來這個方法**不複雜**，大概 15 分鐘你們全部都會懂。」

`[00:23]`【口頭】「如果你在想今天哪裡最重要：**接下來 10 分鐘，醒來。**」

### 4.1 想法：一個大家都信任的第三方

`[00:24]` **可信任機構（trusted authority）**，在這個協定裡叫 **KDC**。
- 「**可信任機構**這個詞接下來幾週會常出現。」
- 它是**所有人都信任**的第三方，「所以**不是 Oscar**」。

`[00:25]` 設定：
- KDC 跟 Alice 共享 $k_A$；跟 Bob 共享 $k_B$。
- 「怎麼送過去？**設定時（setup time）**某個時間點一定要建立這把金鑰。」
- **重點：每個使用者只有一把金鑰**。不管網路是 2 人、4 人還是 750 人。
- 750 人 → KDC 有 $k_1, k_2, \ldots, k_{750}$。

### 4.2 笨方法：KDC 當轉信站

`[00:27]`【口頭】「一個**蠢的**做法（我們不會這樣做）：」
- Alice 用 $k_A$ 加密訊息 → 送到 KDC → KDC 解密，再用 $k_B$ 加密 → 送給 Bob。
- 【口頭】「這安全上可行，因為**金鑰就扮演了安全通道**。」
- 【課堂討論】`[00:28]` 問題？→ **所有流量都要經過 KDC**，變成**通訊瓶頸**。

### 4.3 正確做法：KDC 把「加密過的金鑰」發出去

`[00:28]` Alice 想跟 Bob 通訊（Bob 還不知道）：

**步驟 1：請求**
Alice 送出 $\text{RQST}(ID_A, ID_B)$。ID 可以是名字、社會安全號碼、護照號碼、員工編號…… KDC 就知道「Alice 和 Bob 想通訊」。

**步驟 2：KDC 產生會期金鑰並加密它**（`[00:29]`）
- 產生隨機的**會期金鑰（session key）** $k_{ses}$（以前叫 $k_{AB}$）。
- 【口頭】「**革命性的概念來了，接下來 30–60 秒大家醒著**：我們**加密會期金鑰**。」

$$y_A = e_{k_A}(k_{ses}), \qquad y_B = e_{k_B}(k_{ses})$$

- 【口頭】`[00:30]`「**我們加密金鑰** —— 這是之前沒做過的事。」例如用 AES-256。
- KDC 把 $y_A, y_B$ **都送給 Alice**。

**步驟 3：Alice 解出會期金鑰**（`[00:30]`）
- 【課堂討論】Alice 能拿 $y_A$ 做什麼？→ **解密**：
$$k_{ses} = e^{-1}_{k_A}(y_A)$$
- 【口頭】「會期金鑰算是被**包起來（wrapped）**了。」
- 【課堂討論】她能拿 $y_B$ 做什麼？→ **還不能做什麼**。

**步驟 4：Alice 加密訊息**（`[00:31]`）
$$y = e_{k_{ses}}(x)$$
送出 $y$。

**步驟 5：Bob 怎麼解密？**（`[00:32]`）
- Bob 收到 $y$，看到 Alice 的識別碼，想解密，但**沒有會期金鑰**。
- 【課堂討論】怎麼辦？→ 學生答：**Alice 把 $y_B$ 轉送給 Bob**。「**非常非常好。**」
- Bob 做跟 Alice 一樣的事（`[00:33]`）：
$$k_{ses} = e^{-1}_{k_B}(y_B), \qquad x = e^{-1}_{k_{ses}}(y)$$

```
   Alice                         KDC                          Bob
   KEK: k_A                      KEK: k_A, k_B                KEK: k_B
          ── RQST(ID_A, ID_B) ──→
                                 產生隨機 k_ses
                                 y_A = e_{k_A}(k_ses)
                                 y_B = e_{k_B}(k_ses)
          ←──── y_A, y_B ────────
   k_ses = e⁻¹_{k_A}(y_A)
   y = e_{k_ses}(x)
          ─────────────────── y, y_B ──────────────────→
                                                  k_ses = e⁻¹_{k_B}(y_B)
                                                  x = e⁻¹_{k_ses}(y)
```

【口頭】「（Bob 解密那部非法下載的電影，或你們在幹嘛的東西，Facebook 之類。）」

#### 【Q&A】為什麼 $y_B$ 要繞經 Alice？

`[00:35]`【Q&A】學生問：為什麼 KDC 不直接把 $y_B$ 送給 Bob？
- 教授：「**很好的問題。**課本裡這是**第二個協定**。**第一個協定**就是 $y_B$ 直接送給 Bob，那也沒問題。」
- 「我這版**稍微進階一點**，好處是**通訊比較少**：只有兩次通訊，而不是三次。」
- 「你說的也許比較直覺。實務上可能是 Alice 說『我要寄 email 給 Bob，幫我準備好』，KDC 就把大家準備好。」
- 「**安全上兩種都可以。**」

#### 【Q&A】如果有人拿到 $k_A$ 呢？

`[00:36]`【Q&A】學生提到：如果 $k_A$ 被別人知道了怎麼辦？
- 教授：「**那我就有麻煩了。**如果我把我的金鑰寫下來公開，我就麻煩了。這是密碼學的一部分：某些金鑰**必須保密**。」
- 「但這是**很好的點**，我們幾分鐘後會討論。」（→ 第 5 節）

### 4.4 KDC 的好處

#### 金鑰數量：線性

`[00:37]` **固定（長期）金鑰**：每個使用者**正好一把**。
- $n$ 個使用者 → $n$ 把金鑰對 → **線性複雜度**，不是 $n^2$。
- 【口頭】`[00:39]`「數金鑰還是數金鑰對**不重要**，只差一個 2 倍。重要的是**線性**。」
- 750 人的公司：**只有 750 把金鑰**，不是 280,875。

#### 最大好處：加入新使用者很簡單

`[00:40]`【口頭】「之前 **Noah 是個麻煩製造者**。」
- 現在新使用者加入（例如 Chris），**KDC 只要把 $k_C$ 加進資料庫，就做完了**。
- **只需一條安全通道**，而且**只在設定時**。

【口頭】`[00:41]`「新使用者加入時本來就有工作要做，**很可能那時候本來就有安全通道**。」

#### 【口頭】嵌入式系統的例子：智慧卡個人化

`[00:41]`【口頭】教授研究室做很多**嵌入式**的東西。例子：德國郵局的卡片（⚠️ 逐字稿聽不清楚，「post-punk」可能是「Postbank」）。
- 新智慧卡**在工廠製造**時，安全通道就在**工廠**。
- 叫做**智慧卡個人化（personalization）**：在**輸送帶尾端**把密碼金鑰裝進智慧卡。
- 黏好、焊好之後，最後裝上金鑰。工廠裡有安全通道；交到你手上之後就沒有了。
- 「這時候要更新卡上的 3DES 金鑰**非常困難**，但在工廠裡**很容易**。」

> **在設定時建立一次金鑰，在很多情境下都很實際。**

#### 名詞：金鑰加密金鑰（KEK）

`[00:44]` 固定金鑰 $k_A, k_B, k_C$ 有時叫做**金鑰加密金鑰（Key Encryption Key, KEK）**。

【課本補充】
- **兩種金鑰**：KEK 是**長期金鑰**，不會變；$k_{ses}$ 是**短期金鑰**，常換，理想上每個會期都換。
- 直覺理解：預先分配好的 KEK，就像是 KDC 和每個使用者之間的**秘密通道**；KDC 只是透過這些通道把會期金鑰送出去。
- **付費電視例子**：用 AES 搭配長期 KEK 分配會期金鑰；會期金鑰也許只活**一分鐘**，用**快速的串流密碼**加密電視訊號（為了即時解密）。就算一把會期金鑰外洩，攻擊者也只能解一分鐘的內容。所以會期金鑰用的密碼**不一定要跟**分配金鑰的演算法一樣強。但如果 **KEK 外洩**，過去和未來的流量都能被解密。
- 這些協定都是**金鑰傳送**，不是金鑰協議。

## 5. KDC 的弱點

`[00:44]`【口頭】「剛才有學生說得很好：如果有人拿到 $k_A$，你就有麻煩了。**對攻擊者來說，拿到 $k_A$ 很有吸引力**。」

### 5.1 單點失效

`[00:45]`【口頭】**思想實驗（Gedankenexperiment）**：「這是英文字嗎？對，**韋氏字典**有收。」
- 有一個**仙子**，「我知道沒有仙子，但假裝有」，是個**駭客仙子**，給你**一個願望**：幫你駭進一個系統偷金鑰。
- 選項：Alice、Bob、Chris……或 **KDC**，你選哪個？
- 【課堂討論】→ **KDC**。
- 仙子該帶回什麼？→ $k_A$、$k_B$、$k_C$……**全部**！「光碟、大 USB 隨身碟、1 GB 硬碟，**所有金鑰**。」

> **弱點 1：單點失效（single point of failure）** —— 攻擊者拿到 KDC 的金鑰，你就**真的有大麻煩**。

【課本補充】KDC 被攻破的話，系統裡**所有 KEK 都失效**，要透過安全通道在 KDC 和每個使用者之間**重新建立**。

### 5.2 沒有完美前向保密（PFS）

`[00:46]`【口頭】「**新概念來了，現在要醒過來。**」

情境：仙子比較弱，只成功在 **Alice 的電腦**裝了惡意程式，送出 $k_A$。
- 但 Alice 發現了：防毒軟體跳出警告「$k_A$ 已經外洩」。
- `[00:47]` 怎麼辦？大概**停用它**，雖然很麻煩，還是想辦法弄一條安全通道，建立新的 $k'_A$。
- 攻擊者**沒有 $k'_A$** —— **以後**安全了。

**但過去呢？**（`[00:48]`）
- 如果攻擊者**之前錄下了** $y_A$ 和 $y$：
- 他有 $k_A$ → 解出 $y_A$ 得到 $k_{ses}$ → 解出 $y$ 得到明文。
- 不只昨天的，前天、**去年的**訊息都可以。

```
   過去 ─────────────────────── │ ──────────────→ 時間
   （全部都能被解密！）       k_A 外洩
                              （之後換新金鑰，未來安全）
```

【口頭】`[00:49]`「這是很大的普遍問題。**從現在起**，攻擊者繼續用舊金鑰是傻的，因為你更新了。**問題在過去**：如果你**從不換金鑰**，你就有麻煩。」

> **弱點 2：沒有完美前向保密**
> 【口頭】「這是新名詞，**不是我編的**，而是廣泛使用、**定義清楚的**。」

**定義**（課本 Def. 13.1）：
> 如果**長期金鑰外洩**也**不能讓攻擊者得到過去的會期金鑰**，這個密碼協定就有**完美前向保密（Perfect Forward Secrecy, PFS）**。

【口頭】`[00:51]`
- 「PFS 是**固定術語**。學士或碩士課程裡還有**兩學期的網路安全課**，會大量討論 PFS，別擔心，這只是你們**第一次**碰到。」
- **我們能做什麼？基本上什麼也不能做**，只能接受。
- 「有些協定**有** PFS。**下週或下下週**講公鑰型協定時會看到，有些有、有些沒有。」
- 該做的是：**確保 KDC 的資料庫**（存 750 把金鑰的地方）**非常非常非常安全**。

【課本補充】未來的通訊也一樣：只要 Oscar 有 $k_A$，就能從 KDC 送出的所有 $y_A$ 解出會期金鑰。**Kerberos 和前面的簡單協定都沒有 PFS**；要得到 PFS，主要靠**公鑰技術**。

### 5.3 【課本補充】重放攻擊與金鑰確認攻擊

`[00:52]`【口頭】「其他弱點：**重放攻擊（replay attack）**，還有所謂**金鑰確認攻擊（key confirmation attack）**。這兩個在課本裡，**不複雜**，只是今天**時間不夠**。」
（⚠️ 逐字稿聽不清楚：似乎提到另一位老師（「Dr. ...」）可能會在別的場合講金鑰確認攻擊。）

以下依課本 §13.2.1 整理。這兩個協定擋得住**被動**攻擊者（只能竊聽），但擋不住會**主動**竄改、偽造訊息的攻擊者。

#### 重放攻擊

- Alice 和 Bob **不知道**收到的加密會期金鑰**是不是新的**。如果舊的被重用 → 違反**金鑰新鮮度**。
- 如果某把**舊會期金鑰**外洩了（被駭、或演算法後來被破解）：
- Oscar **冒充 KDC**，把舊的 $y_A, y_B$ 重送給 Alice 和 Bob。
- Oscar 知道那把會期金鑰 → 能解 Alice 或 Bob 加密的明文。

#### 金鑰確認攻擊

前提：**Oscar 也是合法（但惡意）的使用者**，有自己的 KEK $k_O$。

```
   Alice                Oscar                   KDC                    Bob
   KEK: k_A             KEK: k_O                KEK: k_A, k_B, k_O     KEK: k_B
      ── RQST(ID_A,ID_B) ──→
                       換掉成
                           ── RQST(ID_A,ID_O) ──→
                                                隨機 k_ses
                                                y_A = e_{k_A}(k_ses)
                                                y_O = e_{k_O}(k_ses)
      ←─────────────── y_A, y_O ────────────────
   k_ses = e⁻¹_{k_A}(y_A)
   y = e_{k_ses}(x)
      ──── y, y_O ────→
                       攔截
                       k_ses = e⁻¹_{k_O}(y_O)
                       x = e⁻¹_{k_ses}(y)
```

- KDC 以為 Alice 要跟 **Oscar** 建會期；Alice 以為 $y_O$ 是 $y_B$。
- （就算 KDC 在 $y_O$ 前面加上 $ID_O$ 標頭，Oscar 也可以把標頭改成 $ID_B$。）
- 根本原因：**沒有金鑰確認** —— Alice 無法確定**只有 Bob**（而不是別人）知道這把會期金鑰。

## 6. 【課本補充】Kerberos（簡化版）

`[00:51]`【口頭】「有人聽過 **Kerberos** 協定嗎？（大概四個人。）它是一個**很流行、真實世界在用的商業系統**，**以這個方法為基礎**。課本裡有簡化版，比這裡複雜，**但原理就是這個**。你要加上**時間戳記**之類的東西才能讓它真正可用。」

以下依課本 §13.2.2 整理：
- Kerberos 能擋**重放攻擊**和**金鑰確認攻擊**。
- 主要目的其實是電腦網路中的**使用者鑑別**，不只是金鑰分配。
- **1993 年**標準化為 **RFC 1510**，廣泛使用。KDC 在 Kerberos 裡叫做**鑑別伺服器（authentication server）**。

```
   Alice                               KDC                            Bob
   KEK: k_A                            KEK: k_A, k_B                  KEK: k_B
   產生 nonce r_A
        ── RQST(ID_A, ID_B, r_A) ──→
                                       產生隨機 k_ses
                                       產生有效期限 T
                                       y_A = e_{k_A}(k_ses, r_A, T, ID_B)
                                       y_B = e_{k_B}(k_ses, ID_A, T)
        ←────── y_A, y_B ──────────
   (k_ses, r'_A, T, ID_B) = e⁻¹_{k_A}(y_A)
   檢查 r'_A = r_A
   檢查 ID_B
   檢查有效期限 T
   產生時間戳記 T_S
   y_AB = e_{k_ses}(ID_A, T_S)
        ───────────────── y_AB, y_B ─────────────────→
                                         (k_ses, ID_A, T) = e⁻¹_{k_B}(y_B)
                                         (ID'_A, T_S) = e⁻¹_{k_ses}(y_AB)
                                         檢查 ID'_A = ID_A
                                         檢查有效期限 T
                                         檢查時間戳記 T_S
        ───────────────── y = e_{k_ses}(x) ──────────→   x = e⁻¹_{k_ses}(y)
```

**怎麼擋攻擊**：

| 機制 | 擋什麼 |
|---|---|
| **有效期限 $T$**（加密在 $y_A$、$y_B$ 裡） | 雙方都知道會期金鑰能用多久 → 擋重放 |
| **時間戳記 $T_S$** | Bob 確定 Alice 的訊息是**最近的**，不是重放的。雙方時鐘要同步，但精度幾分鐘即可 |
| **nonce $r_A$** | Alice「挑戰」KDC 用 $k_A$ 加密它，傳回來一樣 → 確定 $y_A$ 真的來自 KDC。這叫**挑戰-回應協定（challenge-response）**，智慧卡鑑別常用 |
| **$ID_B$ 放在 $y_A$ 裡** | Alice 確定會期金鑰是給**她和 Bob** 的 → **金鑰確認** |
| **$ID_A$ 放在 $y_B$ 和 $y_{AB}$ 裡** | Bob 確定 (i) KDC 是為他和 Alice 準備的，(ii) 他**現在真的在跟 Alice 講話** |

**KDC 型方案剩下的問題**（§13.2.3）：

| 問題 | 說明 |
|---|---|
| **通訊需求** | 每次新會期都要聯絡 KDC。效能問題，不是安全問題。Kerberos 可以拉長 $T$ 來緩解；實務上能跑**數萬**使用者，但擴展到「所有網路使用者」會有問題 |
| **初始化時要安全通道** | 新使用者加入時要傳送他的 KEK |
| **單點失效** | 存 KEK 的資料庫 |
| **沒有 PFS** | Kerberos 也沒有 |

## 7. 一頁速查表

### 7.1 名詞

| 名詞 | 意思 |
|---|---|
| **金鑰傳送** | 一方選金鑰，安全地傳給別人（KDC） |
| **金鑰協議** | 雙方都貢獻（Diffie-Hellman） |
| **安全通道** | 例：系統管理員親自上傳、工廠裡、信差 |
| **TA（可信任機構）** | 大家都信任的第三方，不是 Oscar |
| **KDC** | 金鑰分配中心，跟每個使用者共享一把 KEK |
| **KEK** | 金鑰加密金鑰：長期、固定 |
| **會期金鑰 $k_{ses}$** | 短期，常換 |
| **PFS（完美前向保密）** | 長期金鑰外洩，**過去**的會期金鑰仍然安全 |
| **KDF** | 從共享秘密衍生新的會期金鑰，要是**單向**的 |

### 7.2 n² 方案 vs KDC

| | n² 方案（每對一把） | **KDC** |
|---|---|---|
| 每人存幾把 | $n-1$ | **1** |
| 系統金鑰對數 | $n(n-1)/2$ | **$n$** |
| 750 人 | 280,875 對 | **750** |
| 加入新使用者 | 跟**所有人**建安全通道 | **只跟 KDC** 建一次 |
| 適用 | 小而**靜態**的網路（分公司、某些銀行網路） | 中大型網路 |
| 弱點 | 擴展性差 | **單點失效**、**沒有 PFS**、重放、金鑰確認 |

### 7.3 KDC 協定（課堂版）

1. Alice → KDC：$\text{RQST}(ID_A, ID_B)$
2. KDC：$y_A = e_{k_A}(k_{ses})$，$y_B = e_{k_B}(k_{ses})$ → 都給 Alice
3. Alice：$k_{ses} = e^{-1}_{k_A}(y_A)$，$y = e_{k_{ses}}(x)$
4. Alice → Bob：$(y, y_B)$
5. Bob：$k_{ses} = e^{-1}_{k_B}(y_B)$，$x = e^{-1}_{k_{ses}}(y)$

## 附：本講一句話總結

> **對稱密碼要先有共享金鑰：讓每一對使用者都直接共享金鑰（n² 方案）時，金鑰數量會平方成長，而且每加一個人就要跟所有人重建安全通道；改用一個大家都信任的 KDC，每人只需跟 KDC 共享一把 KEK，由 KDC 把「用 KEK 加密過的會期金鑰」發給雙方，金鑰數變成線性、加人也容易，但代價是 KDC 成為單點失效，而且一旦 KEK 外洩，過去錄下的通訊全部能被解密（沒有完美前向保密）。**
