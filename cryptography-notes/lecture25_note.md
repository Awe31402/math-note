## 1. MAC 的原理

### 1.1 回顧：數位簽章（「今天暗無天日」）

`[00:03]`【口頭】數位簽章的原始動機：把「在文憑上簽名」這件事搬到數位世界 —— 確保東西**真的來自那個人**（發送者真實性 / 訊息鑑別）。

【口頭】`[00:05]`「有點像**《今天暫時停止》（Groundhog Day，德文 Und täglich grüßt das Murmeltier）**那部電影。誰看過？你們會再經歷一遍：如果你看四週前的影片，我就是這樣開場的。」

```
   Alice                                Bob
              ←────── k_pub ──────    (k_pr, k_pub)
                                      s = sig_{k_pr}(x)
              ←────── (x, s) ──────
   ver_{k_pub}(x, s) = true / false
```

【課堂討論】Alice 做的運算叫什麼？→ **驗證**。

### 1.2 為什麼要用對稱密碼做

`[00:07]`【課堂討論】數位簽章很安全、還有不可否認性之類的好東西，為什麼要離開公鑰簽章？
→ 學生答：**對稱比較快**。

【口頭】
- 「公鑰很棒，能在不安全的通道上交換金鑰，能做各種神奇的事。**但它們真的很慢，很麻煩。**」
- 「如果不必用它，有替代方案很好。很多情況可以用**區塊密碼和雜湊函數**得到**很類似（但不完全一樣）**的結果。」
- 「所以數位簽章還是需要，但有對稱的選擇不壞。」

### 1.3 MAC 的基本協定

`[00:09]` 現在 Bob 沒有公私鑰對，只有**對稱金鑰 $k$**，要跟 Alice 共享。

【口頭】「怎麼把金鑰送過去？**不容易**，但這屬於公鑰密碼學的範圍。**接下來兩三講**我們會談金鑰分配。」

```
   Alice                                    Bob
     k ←──────── 共享的秘密金鑰 ────────→ k
                                         m = MAC_k(x)
              ←────── (x, m) ──────
   m' = MAC_k(x)
   m' =? m
```

| 步驟 | 說明 |
|---|---|
| Bob 算 MAC | $m = \text{MAC}_k(x)$。【口頭】「不叫 sig，叫 MAC。結果不叫 $s$，叫 $m$ —— 這不太好，因為**很多書用 $m$ 表示訊息**，我們用 $x$。」 |
| Bob 送出 | $(x, m)$。$m$ 就是附加上去的**密碼學檢查碼** |
| Alice 驗證 | 【口頭】`[00:11]`「數位簽章要跑驗證演算法。看 Elgamal 簽章，簽和驗**很不一樣**。這裡是**對稱**的，所以 Alice 做**完全一樣的事**：**重新計算 MAC**，得到 $m'$。」 |
| 比較 | 【課堂討論】最後一步？→「**很簡單**：比較」$m' \stackrel{?}{=} m$ |

【口頭】`[00:12]`「這個『等號加問號』是我的**蠢記號**，全世界只有這裡在用（我誇張了），**絕對不是密碼學的標準記號**。但我覺得很有用。」

> **MAC = 發送方算、接收方重算、比較。**

### 1.4 MAC 的性質

`[00:13]` 只看協定、不管演算法細節，**希望有的性質**：

**任意長度的輸入**（`[00:14]`）
- 【口頭】「數位簽章有個問題：RSA 用 2000 bit 模數，訊息就限制在 2000 bit，大約 250 byte，**很麻煩**，所以要引入雜湊函數之類的。」
- 「希望 MAC **馬上**就能吃任意長度：100 個字的 email、100 MB 的 PDF 都行，**不必先雜湊**。」

**固定長度的輸出**（`[00:15]`）
- 「丟 100 個字進去，大概得到很短的 MAC；丟 100 MB 的 PDF 進去，**最好也很短**。不管輸入多長，都是很短的密碼學檢查碼。」

【課本補充】課本整理的 MAC 七個性質：

| # | 性質 |
|---|---|
| 1 | **密碼學檢查碼**：產生密碼學上安全的鑑別標籤 |
| 2 | **對稱**：基於秘密的對稱金鑰，簽和驗的兩方要共享金鑰 |
| 3 | **任意長度訊息** |
| 4 | **固定長度輸出** |
| 5 | **訊息完整性** |
| 6 | **訊息鑑別** |
| 7 | **沒有不可否認性** |

### 1.5 安全服務

#### 訊息鑑別

`[00:16]`【課堂討論】如果驗證通過（$m'$ 剛好等於 $m$ 的那 128 bit），Alice 知道訊息來自 Bob 嗎？

- 有學生說：**不知道**，Oscar 可以用**別的金鑰**算一個 MAC，把 $x$ 和新的 $m$ 一起送。
- 教授：「**好討論、好點子**，但行不通。**Alice 沒有 Oscar 的金鑰**。這是一個**很好的錯誤輸入**。」
- 要算出有效的 $m$，**必須知道秘密金鑰**。驗證通過 → 一定是**知道 $k$ 的人**算的。

【口頭】`[00:17]`「這是**兩學期以來一直的假設**，你可能沒注意到：**這些協定都只在金鑰分配正確時才有效**。如果 Oscar 有 $k$，當然一切都完了 —— 所以我們叫它**安全**通道，不然就叫『漏水的通道』了。」

> ✔ **有訊息鑑別（發送者真實性）**

#### 完整性

`[00:19]` 情境：$x$ = 「轉 10 元到 Oscar 的帳戶」，Oscar 想換成 $\tilde{x}$ = 「轉 10,000 元」。

【課堂討論】Alice 察覺得到嗎？驗證會通過嗎？→ **不會**。輸入不同了；「細節我們還不知道，大概是區塊密碼或雜湊函數，翻一個 bit 整個輸出就變隨機了」。

> ✔ **有完整性**（傳輸中沒被改）

#### 不可否認性

`[00:21]`【課堂討論】跟數位簽章相關的第三個**非常重要**的安全服務？「線上買福斯 Golf 那個例子……沒人記得？」→ **不可否認性（Nicht-Zurückweisbarkeit）**。

`[00:22]` 情境：Bob 線上訂車（網頁表單、合約）+ MAC 送給車商 Alice。之後 Bob 說「我沒訂」，Alice 把 Bob **拖上法庭**（vor Gericht zerren）。

【課堂討論】Bob 能向法官證明嗎？→ 學生答：**Alice 也可能自己產生，送給自己**。「**完全正確。**這是**對稱設定**，Bob 能產生，Alice 也能。法官無法判斷是誰做的。」

> ✘ **沒有不可否認性**

【口頭】`[00:24]`「如果 MAC 有不可否認性，那它跟數位簽章**幾乎一樣功能**，我們就不需要數位簽章、不需要那些大數算術了。」

> **MAC 對 Alice 或 Bob 本人作弊的情況沒有保護**（壞人不是 Oscar，而是通訊的其中一方）。

【課本補充】
- 對稱金鑰**不綁定某個人**，而是綁定**兩方**，所以有爭議時法官無法分辨。
- 實務上 MAC 主要用兩種方式建構：**用區塊密碼**或**用雜湊函數**。

## 2. 用雜湊函數做 MAC

`[00:25]` 第二章，今天比較大的部分：**怎麼實現 MAC**。

### 2.1 想法：把金鑰和訊息一起雜湊

`[00:26]`【口頭】「我們想把**金鑰和訊息綁在一起**。一個**令人驚訝地簡單**的做法：」

- 雜湊函數 $h$ 很會把東西**攪在一起**。
- 把 $k$ 和 $x$ 都丟進去當輸入 → 輸出 $m$ 是 $x$ 和 $k$ 的函數。
- 雜湊函數有那些好性質，所以**很難攻擊**。

**問題：怎麼混合 $k$ 和 $x$？**（`[00:28]`）兩個顯而易見的做法：

| 名稱 | 公式 | 說明 |
|---|---|---|
| **Secret prefix MAC** | $m = h(k \,\|\, x)$ | 先金鑰（例如 128 bit），再接 2 MB 的 PDF。（prefix = 字首，德文 Vorsilbe） |
| **Secret suffix MAC** | $m = h(x \,\|\, k)$ | 【課堂討論】另一個？→「**反過來**」。（suffix = 字尾，Nachsilbe） |

【口頭】`[00:29]`「**兩個看起來都很直覺，但就像密碼學常常發生的：兩個都是爛主意。**」
「最後的 HMAC 其實很簡單，**基本上是把兩者結合**。但我想先讓你們看兩者的弱點，**讓你們感受密碼學有多狡猾**。」

### 2.2 Secret Prefix MAC 的弱點：附加攻擊

#### 先看雜湊函數怎麼處理長訊息

`[00:32]`
- $x$ 可能是 2 MB 的 PDF 或 2 GB 的硬碟分割區。
- 實際上 $x$ **被切成區塊** $x_1, x_2, \ldots, x_n$，**逐塊雜湊**，「這會是個重點」。
- 【課堂討論】SHA-1 一個輸入區塊多大？→ 很大（512 bit）。
- 所以 secret prefix 實際上是：$h(k \,\|\, x_1 \,\|\, x_2 \,\|\, \cdots \,\|\, x_n)$

大部分雜湊函數用 **Merkle-Damgård 結構**（`[00:34]`，「我們最愛的丹麥人的梯子結構」）：

```
IV ──→ [壓縮] ──→ [壓縮] ──→ [壓縮] ──→ … ──→ [壓縮] ──→ m
         ↑          ↑          ↑                 ↑
         k          x₁         x₂                x_n
```

每一塊的輸出，就是下一塊的「初始值」。

#### 攻擊

`[00:37]` Bob 照規矩算 $m = h(k \| x_1 \| \cdots \| x_n)$，送出 $(x, m)$。

【口頭】`[00:38]`「**睡著或在講話的人，停下來。**這很重要，而且**在很多書裡不容易找到**。**可能會考。**很多好理由要專心 3 分鐘。」

Oscar 攔截，在訊息後面**附加一個自己選的區塊** $x_{n+1}$：

$$x_O = (x_1, x_2, \ldots, x_n, x_{n+1})$$

【口頭】「例如這是一份**合約**，結尾常有**附件（Anhang）**，有時候很重要。Oscar 可以加上**自己的附件**。」
（教授用手寫體的 $O$ 表示 Oscar，「免得跟 0 搞混，**也不是橢圓曲線的無窮遠點**」。）

**他要怎麼算新訊息的 MAC？**（`[00:40]`）
- 如果 Bob 自己想加 $x_{n+1}$：他會把 $k, x_1, \ldots, x_n$ 一塊塊丟進去，到 $x_n$ 之後的值是什麼？
- 【課堂討論】→ **就是 $m$**！
- 所以要多處理一塊，**只要拿 $m$ 當初始值**，再雜湊 $x_{n+1}$：

$$\boxed{m_O = h(m \,\|\, x_{n+1})}$$

> **完全不需要金鑰 $k$！**

**Alice 驗證**（`[00:42]`）：「Alice 是個乖女孩，照規定**重算 MAC**」：
$$m' = h(k \| x_1 \| \cdots \| x_n \| x_{n+1}) = m_O \;✔$$

→ Alice 接受 $(x_O, m_O)$ 為有效，雖然 Bob 只認證了 $(x_1, \ldots, x_n)$。

```
   Alice                     Oscar                          Bob
                                                   m = h(k‖x₁‖…‖x_n)
                         ←────── (x, m) ──── 攔截 ─────
                         x_O = (x₁,…,x_n, x_{n+1})
                         m_O = h(m ‖ x_{n+1})
             ←── (x_O, m_O) ──
   m' = h(k‖x₁‖…‖x_{n+1})
   m' = m_O → 有效！
```

#### 但這有一點簡化

`[00:43]`【課堂討論】上週 Merkle-Damgård 的圖還少了一塊，是什麼？→ **填充（padding）**。

- 真正的 Merkle-Damgård 要求用**含長度資訊的填充**：在處理時加入訊息有幾個區塊（或幾個 byte）。
- 這樣的話，訊息變長了，長度資訊不符 → **攻擊失敗**。
- 但如果雜湊函數**沒有**含長度資訊的填充，攻擊就成立。

> 【口頭】`[00:45]`「嚴格照 Merkle-Damgård 做，這個攻擊行不通，**但這仍然不是好狀況**。總結這 10 分鐘：**不要這樣做**，因為 Oscar 可能在訊息後面加壞東西。」

【課本補充】攻擊之所以可行，是因為額外區塊的 MAC **只需要前一個雜湊輸出（= Bob 的 $m$）和 $x_{n+1}$**，**不需要金鑰**。

### 2.3 Secret Suffix MAC 的弱點：碰撞攻擊

`[00:46]`【口頭】「既然先放金鑰有問題（可以在後面加東西），**那反過來**：先雜湊 $x$，最後才放金鑰。**現在出現另一個問題**，跟雜湊函數的性質比較有關，我覺得接下來的討論很好。」

**假設 Oscar 能找到碰撞**：$x \ne x_O$，但

$$h(x) = h(x_O)$$

例如 $x$ =「轉 10 元」、$x_O$ =「轉 10,000 元」—— 兩份意思不同的合約或交易。

**為什麼這有問題**（`[00:49]`）：
- 先迭代雜湊 $x_1, \ldots, x_n$，得到某個中間值；同樣雜湊 $x_O$ 的區塊，得到**同一個**中間值（因為碰撞）。
- 然後在最後**接上金鑰** $k$。
- 兩邊的中間值一樣、最後一塊 $k$ 也一樣 → **最終輸出一樣**：

$$m = h(x \,\|\, k) = h(x_O \,\|\, k)$$

【口頭】`[00:51]`「這個攻擊**更簡單**：Oscar 攔截後**連 $m$ 都不用改**，只要把 $x$ 換成 $x_O$。」

#### 但 Oscar 得先找到碰撞，值得嗎？

`[00:52]`【口頭】「這裡的假設是 Oscar 要做**更多工作**：他得找到碰撞，『這不是週日下午喝咖啡吃蛋糕就能做的』，找碰撞**非常難**。**問題是：這仍然給 Oscar 優勢嗎？**」

【課堂討論】`[00:53]` 對對稱密碼**永遠可用**的通用攻擊？→ **暴力搜尋**。
→ 所以問題是：**找碰撞會不會比暴力搜尋金鑰還容易？**

**具體例子**（`[00:54]`）：用 **SHA-1**（輸出 160 bit，超流行）、金鑰 **128 bit**（常見的安全等級，例如搭配 AES-128）。
- 期望：攻擊者要 $2^{128}$ 步（「宇宙的壽命之類的」）。

| Oscar 的選擇 | 複雜度 |
|---|---|
| 暴力搜尋金鑰 | $2^{128}$ |
| 天真地找碰撞（第二原像） | $2^{160}$ |
| 【課堂討論】更好的辦法？關鍵字？→ **生日悖論** | $\sqrt{2^{160}} = \mathbf{2^{80}}$ |

【口頭】`[00:58]`「兩週前我們用紙傳生日的實驗有找到碰撞嗎？我還有點擔心數學不靈，結果是靈的。通常第 19 個人左右就會有人打叉說『我撞了』，**這次花比較久**。」

> **結論**：如果雜湊輸出**不夠長**，你就**拿不到預期的密碼強度** —— 生日悖論讓攻擊者佔了便宜（$2^{80} < 2^{128}$）。**Secret suffix 也不行。**

【課本補充】而且有跡象顯示 SHA-1 的碰撞**可以用更少步數**構造（第 21 講），所以實際攻擊可能更容易。

### 2.4 HMAC

`[00:59]`【口頭】「幸好有一個**酷的**做法，比前面兩個**稍微複雜一點，但其實不複雜**。不是另一個 SHA-1 那種東西。」

#### 背景

`[01:00]`【口頭】給一點歷史脈絡：
- DES 約 1975 年提出；1976、77 年 DH 和 RSA 提出。
- **HMAC：1996 年**由 **Bellare、Canetti、Krawczyk** 提出（「我不寫名字了」）。
- 用在 **SSL / TLS** —— 瀏覽器裡那個**小鎖頭**。連到 Facebook 之類，小鎖頭亮起來時就在用。

【口頭】「（順便說，secret suffix 的碰撞問題，就算做了正確的填充也**避免不了**。所以我們想**遠離 secret suffix**，但 **secret prefix 可以修好**。）」

#### 基本想法：兩層巢狀雜湊

`[01:01]`【口頭】「想法是**兩個巢狀的（verschachtelt）**雜湊。**別講話 40 秒，我保證。**」

1. 先做 secret prefix：$h(k \,\|\, x)$ → 這叫**內層雜湊（inner hash）**
2. 再套一層：$h(k \,\|\, \text{內層結果})$ → **外層雜湊（outer hash）**

（直覺上：附加攻擊能延伸內層雜湊，但延伸不了外層，因為外層的輸入**又從金鑰開始**。）

【口頭】「好了，你可以回去看 YouTube 了……**開玩笑的，專心**。」

#### 完整的 HMAC

`[01:04]` 實際上還要**處理金鑰**（擴展、加 padding），「不完全那麼簡單，但幾乎一樣簡單」。

$$\boxed{\text{HMAC}_k(x) = h\Big[\,(k^+ \oplus \text{opad}) \,\Big\|\, h\big[(k^+ \oplus \text{ipad}) \,\|\, x\big]\,\Big]}$$

| 元件 | 意思 |
|---|---|
| **$k^+$** | **擴展後的金鑰**：在金鑰**左邊補 0**，補到雜湊函數的**輸入區塊寬度 $b$**（SHA-1 是 512 bit）。【口頭】「雜湊函數的輸入很長，512 或 1024 bit，但金鑰很少那麼長，通常 128 或 256。128 bit 要補到 512 bit，就補大約 400 個 0。」 |
| **ipad** | **內層填充（inner pad）**：固定 bit 圖樣 `0011 0110`（= `0x36`）**重複**到 $b$ bit。SHA-1 的話是 512 bit = 64 byte → 重複 **64 次** |
| **opad** | **外層填充（outer pad）**：固定 bit 圖樣 `0101 1100`（= `0x5C`）重複到 $b$ bit |
| 內層 | $(k^+ \oplus \text{ipad})$ 當第一塊，接著訊息區塊 $x_1, \ldots, x_n$ |
| 外層 | $(k^+ \oplus \text{opad})$ 當第一塊，接著**內層雜湊的輸出** |

【口頭】
- 「ipad、opad 是**兩個固定的 bit 圖樣**，寫在標準裡，不是我想出來的。」
- 「1996 年，**比真正的 iPad 早**。」
- 「（最後兩分鐘了，但**填完教學評鑑才能走**。）」

```
           k⁺ ⊕ ipad      x₁       x₂     …    x_n
              │           │        │            │
   IV ──→ [壓縮] ──→ [壓縮] ──→ [壓縮] ──→ … ──→ [壓縮] ──→ 內層輸出
                                                              │
           k⁺ ⊕ opad                                          │
              │                                               │
   IV ──→ [壓縮] ──────────────────────────────→ [壓縮] ──→ HMAC
```

（教授說可以對照課本 Figure 12.2，第一版第一刷在 p.324 或 325，「你們手上的可能是新版」。）

#### 重點：效率幾乎沒有損失

`[01:13]`【口頭】「**停一下，40 秒就好。很簡單但很重要：**」
> 「你可能會說：Paar 教授說這很安全，**但要做兩次雜湊**。這其實**是騙人的**。」
> - **長訊息只雜湊一次**（在內層）。就算 2 MB 也只一次。
> - **外層只有兩個輸入區塊**：$(k^+ \oplus \text{opad})$ 和內層輸出。
> - 「所以**額外的計算量非常非常小**。」

> **訊息只被處理一次。**

【課本補充】
- 雜湊輸出長度 $l$（SHA-1 是 160 bit）和輸入區塊寬度 $b$（512 bit）不一樣沒關係，雜湊函數本身有前處理會補齊。
- **HMAC 有安全性證明**：如果 Oscar 能破 HMAC（不知道金鑰卻能產生有效標籤），他就能破所用的雜湊函數（找到碰撞，或在不知道初始值 IV 的情況下算出雜湊輸出）。
- 也用在 **IPsec**。常搭配 SHA-1、MD5，未來會越來越多搭配 SHA-2、SHA-3。

## 3. 【課本補充】用區塊密碼做 MAC

課堂沒講，依課本 §12.3–12.5 整理。

### 3.1 CBC-MAC

**最流行的做法**：把 AES 之類的區塊密碼用在 **CBC 模式**（第 9 講）。

**產生 MAC**：
1. 訊息切塊 $x_1, \ldots, x_n$
2. $y_1 = e_k(x_1 \oplus IV)$（IV 可以公開，但要隨機）
3. $y_i = e_k(x_i \oplus y_{i-1})$
4. **MAC 就是最後一塊的輸出**：$m = \text{MAC}_k(x) = y_n$

**跟 CBC 加密的差別**：中間的 $y_1, \ldots, y_{n-1}$ **不送出**，只是內部值。

**驗證**：重做一次，比較 $m' \stackrel{?}{=} m$。（**跟 CBC 解密不一樣**，解密是反向運算。）

**輸出長度**：等於區塊大小。歷史上 **DES** 很常用（例如銀行）；現在常用 **AES** → 128 bit 的 MAC。

### 3.2 GMAC

- **GCM 模式**（第 9 講）的變形：**不加密，只算 MAC**。
- **容易平行化** → 適合高速應用。
- 用在 **IPsec**（ESP、AH），提供資料來源鑑別但不提供機密性。
- 硬體上可達 **10 Gbit/s** 以上。

### 3.3 其他

| 方案 | 說明 |
|---|---|
| 歷史 | 1977 年（DES 發表幾年後）就有人提議用 DES 算檢查碼；之後在美國標準化，用於金融交易完整性（ANSI X9.17） |
| **CMAC** | NIST 建議，類似 CBC-MAC；AES-CMAC 在 RFC 4493 |
| OMAC、PMAC | 也以區塊密碼建構 |
| **CCM** | Counter with CBC-MAC，認證加密模式 |
| **UMAC** | 基於**通用雜湊（universal hashing）**，軟體上非常快（每 byte 約一個時脈） |

## 4. 一頁速查表

### 4.1 MAC vs 數位簽章

| | 數位簽章 | **MAC** |
|---|---|---|
| 金鑰 | 公私鑰對 | **對稱金鑰**（雙方共享） |
| 產生 | $s = \text{sig}_{k_{pr}}(x)$ | $m = \text{MAC}_k(x)$ |
| 驗證 | $\text{ver}_{k_{pub}}(x, s)$（跟簽很不一樣） | **重算** $m' = \text{MAC}_k(x)$，**比較** $m' \stackrel{?}{=} m$ |
| 速度 | 慢 | **快** |
| 訊息鑑別 | ✔ | ✔ |
| 完整性 | ✔ | ✔ |
| **不可否認性** | ✔ | **✘** |
| 也叫 | — | 密碼學檢查碼、帶金鑰的雜湊 |

### 4.2 三種雜湊式 MAC

| 方案 | 公式 | 弱點 |
|---|---|---|
| Secret prefix | $h(k \| x)$ | **附加攻擊**：$m_O = h(m \| x_{n+1})$，不需金鑰（Merkle-Damgård 含長度填充可擋） |
| Secret suffix | $h(x \| k)$ | **碰撞攻擊**：$h(x) = h(x_O) \Rightarrow$ 同一個 MAC；生日攻擊只要 $2^{l/2}$（SHA-1：$2^{80} < 2^{128}$） |
| **HMAC** | $h[(k^+ \oplus \text{opad}) \| h[(k^+ \oplus \text{ipad}) \| x]]$ | 有安全性證明 |

### 4.3 HMAC 細節

| 項目 | 內容 |
|---|---|
| 提出 | 1996，Bellare、Canetti、Krawczyk |
| 用在 | **TLS**（瀏覽器小鎖頭）、IPsec |
| $k^+$ | 金鑰左邊補 0 到區塊寬度 $b$（SHA-1：512 bit） |
| ipad | `0x36` 重複 $b/8$ 次 |
| opad | `0x5C` 重複 $b/8$ 次 |
| 效率 | 訊息**只雜湊一次**；外層只有 2 塊 → 額外成本很小 |

### 4.4 CBC-MAC

$$y_1 = e_k(x_1 \oplus IV), \quad y_i = e_k(x_i \oplus y_{i-1}), \quad m = y_n$$

## 附：本講一句話總結

> **MAC 是用對稱金鑰做的「數位簽章」：發送方算一個密碼學檢查碼、接收方重算比對，能提供訊息鑑別和完整性，但因為雙方有同一把金鑰，給不了不可否認性；把金鑰和訊息直接串起來雜湊並不安全（放前面會被附加區塊、放後面會被碰撞），正確做法是 HMAC —— 用兩層巢狀雜湊，而且長訊息仍然只需雜湊一次。**
